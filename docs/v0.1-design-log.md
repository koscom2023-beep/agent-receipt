# agent-guard v0.1 설계 로그 (verify/check 분리 + verify --json)

> 14인 전문가 회의(악마의 대변자 포함, 정반합 2라운드)로 확정한 설계 근거 기록.
> 권위 소스는 코드다 — 본 문서와 코드가 어긋나면 코드가 맞다.

## 범위 (사장님 승인분)

- `verify`는 더 이상 `required_checks.commands`를 실행하지 않는다(상태 검사만).
- 새 `check` 명령이 `required_checks.commands`만 실행한다.
- `verify --json` = **spec 필드만 추린 stable JSON**(`JSON.stringify(result)` 통째 출력 금지).
- 변경 파일: `src/checks.ts`, `src/cli.ts`, `src/output.ts`, `README.md`, `test/run-fixtures.ts`(신규).
  본 설계 로그(`docs/`)는 기능 변경이 아니라 근거 기록이므로 별도.

## 금지 (불가침)

`verify --with-checks` / 새 deps·테스트 프레임워크 / `package.json`·lock·`tsconfig.json`·`schema.ts`·`git.ts`·`contracts/` 변경 / `output.ts`의 `printReport`·`toMarkdown`·`buildPrompt` 변경 / `git diff -M` / pre-push·hook·`guard new`·allow-path·dashboard·SaaS / promptia·DB·push·deploy.

## 악마의 대변자 — 잔존 보증 불가 (정직 기록)

1. **verify-only fail-open**: "verify는 commands 금지"가 불가침인 한, verify만 돌린 주체는 명령 미실행 상태로 PASS를 받는다. `--json` 메타필드 금지(spec-only)라 기계가 "verify-only"를 판별할 채널도 없다. → 완화는 **워크플로우 규율(`verify && check`)**뿐이며 도구 자체로는 봉인 불가. 코드가 아니라 운영 규약에 의존하는 잔존 위험으로 명시.
2. **`test/`의 tsc 사각**: `tsconfig.include`가 `src/**`라 `tsc --noEmit`는 fixture 파일을 타입체크하지 않는다(`tsconfig`는 변경 금지). fixture는 서브프로세스 방식이라 thin glue(node 내장 모듈만 사용)이고 검증 대상 실제 로직(cli/checks/output)은 `tsc`가 본다 → 위험은 낮으나 0은 아님. fixture 자체 로직 버그는 최초 작성 시 사람 리뷰에 의존. tsc 분리 보고(아래)로 정직 표기.
3. **`spawnError` 미가시화**: missing-binary(ENOENT)는 현재 `runCommand`에서 exitCode 1로 떨어진다. 샘플 계약이 모두 `required_exit: 0`이라 ENOENT가 우연히 PASS로 새는 함정은 v0.1에서 비현실적 → 별도 필드 추가는 YAGNI로 보류(차기 과제).

## 보고 분리 원칙

`tsc --noEmit`(= `src/**` 검증)와 fixture(= tsx 런타임 실행)는 **서로 다른 명령·다른 커버리지**다. "한 번에 일괄 통과"로 뭉뚱그리지 않고 분리 보고한다. self-verify(agent-guard로 자기 검증)는 self-contract가 없고 `contracts/`가 변경 금지라 **미수행**으로 둔다(허위 self-pass 금지).
